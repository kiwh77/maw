## 结论先行

值得借鉴。最适合 maw 的方向，是在现有跨工程任务中枢上增加执行过程观测和交付复盘：既能看现在谁在做什么，也能解释一个任务经历了哪些阶段、在哪里等待、为什么反复返工。

截图的核心价值在于“总览 → 时间段 → 单个对象 → 轮次明细”的连续下钻。对 maw，应先落到“工程 → 任务 → 执行批次 → 事件”，之后有真实采集能力再关联会话与轮次。

| 截图能力 | 判断 | maw 的落地方式 | 优先级 |
| --- | --- | --- | --- |
| 按工程聚合、统一筛选、详情下钻 | 直接采用信息结构 | 复用现有工程筛选与任务抽屉，补历史时间范围与工程摘要 | 高 |
| 小时协作时间轴 | 改造后采用 | 先展示任务阶段驻留区间、阻塞、提交和合入节点 | 高 |
| 全天活动热图 | 改造后采用 | 初期按已记录事件计数，明确称“事件活跃度”；有执行区间后再展示执行时间覆盖 | 中 |
| AI 执行／等待／输入点 | 依赖新数据后采用 | 增加执行、轮次边界及等待原因，不能用任务状态直接替代 | 中 |
| 会话与轮次明细 | 分阶段采用 | 将会话作为任务的关联上下文，优先支持一个可验证的数据来源 | 中 |
| 已知 Token | 有来源与覆盖率后采用 | 保留未知值，区分累计读数、增量、缓存口径和重复采集 | 后续 |

| 按工时／Token 排名、给人打分 | 不采用 | 不能由投入量直接判断交付质量 | 不排期 |

## 统计口径必须先明确

### 任务阶段与 AI 执行分开

`in_progress` 表示任务处于执行阶段，期间可能包含模型执行、工具运行、人在查看结果、等待输入、客户端离线等情况。现有 `Progress` 更新的是心跳与进度消息，不能还原这一整段内的真实执行区间。

第一版适合展示：

- 任务进入执行阶段到提交的经过时间；名称明确为“执行阶段驻留”。
- 进入评审、合并阶段到离开的驻留时间。
- 明确记录的阻塞区间及原因。
- 提交、合入、失败、重新进入执行阶段的事件节点。

这些首先用于发现阶段停留，不应直接命名为“AI 工时”“人工等待”或“评审耗时”：阶段内部发生了什么，尚需更细事件。

### 并行指数不等于效率提升

如截图采用下述口径，300 分钟累计执行除以 180 分钟执行区间并集，约为 1.7：

`活跃期间平均并发 = 各执行区间时长之和 ÷ 所有执行区间的并集时长`

这表示有 AI 活跃时平均多少条执行重叠。若改用整个统计窗口作为分母，得到的是窗口平均并发，数值与意义不同。

两者都不能证明“节省了 1.7 倍人力”。重复劳动、失败重试也能提高并发和 Token。maw 应同时展示完成合入、阻塞、返工与数据覆盖情况，帮助判断这些投入带来了什么。

### 无事件不代表人在等待

空白区间可能是暂停、断线、漏报，也可能是用户转去处理其他任务。只有明确的 `waiting_user`、`waiting_approval` 等记录，才能归入对应等待原因。心跳缺失宜显示“状态过期／执行情况未知”。

当前心跳过期处理还可能把任务退回 ready 或 blocked；这属于调度恢复行为，不是某轮 AI 执行结束的证明。见 [过期处理](../internal/app/heartbeat.go:11)。

### Token 要允许不知道

未知值用 `null`／“未采集”，不能用 0。至少区分来源、模型、输入、输出、缓存，以及累计读数或单轮增量。若同一轮同时来自实时上报与日志回放，应按稳定来源标识去重。

覆盖率应说明分母，例如“有完整 Token 的轮次／已观测轮次”，不能声称覆盖了未接入工具中的全部使用。首版先显示原始用量；费用计算需要另行维护并验证模型价格和计费规则。

## 接入时需要补齐的基础

### 1. 给历史执行独立身份

工程、任务与会话不是一条固定的一对多链：一个任务可能跨多个会话，一个会话也可能连续完成多个任务。Agent 名是工作者身份，同样不能代替会话标识。

建议采用以下对象与关系，作为新设计而非现有实现描述：

| 对象 | 用途 |
| --- | --- |
| `project_id` | 工程身份 |
| `task_instance_id` | 区分同一显示编号的不同任务实例／重建 |
| `run_id` | 一次领取执行至提交、失败、释放等结束的批次 |
| `source + session_id + turn_id` | 标识外部工具的会话与轮次 |
| 执行与任务关联 | 允许会话／轮次关联多个任务；无法确认时保留未归属 |

现有 `attempts` 在部分失败路径增长，不能直接当作完整运行批次计数。历史无法区分的段落保留原始事件，并展示不确定性。

### 2. 让事件可重放、可去重

当前事件有本机入库时间、工程、actor、类型、任务和自由载荷，适合业务日志，但不足以完整承载异步执行遥测。建议新契约增加版本、来源事件 ID、发生时间、接收时间、执行身份、来源类型与质量标记，并区分去重键与本地递增游标。

执行侧可扩展 start／complete／fail／cancel、明确等待原因和 usage 等事件。工具内部执行状态应进入独立观测模型，避免把正在等待输入直接写成任务被业务阻塞。

参考现有 [AppendEvent](../internal/db/db.go:536)、[StatusReport](../internal/board/serve.go:14)。当前 `client` 写在特定事件载荷中，尚不是完整、稳定的来源实体。

### 3. 历史查询不能只复用现有短列表

任务详情目前读取按时间正序的前 200 条事件；没有历史分页时，长任务后面的完成节点可能不在返回结果内。见 [任务详情入口](../internal/app/helpers.go:364)、[查询排序与上限](../internal/db/db.go:640)。

富事件推送也存在静态代码可见的遗漏路径：feed 每次最多 200 条，watch 读完一批后会将游标直接推进到快照最大事件 ID。若积压超过一页，中间部分不会由该次 SSE watch 继续补齐；数据库本身的事件仍在。见 [feed 上限](../internal/app/status_cmd.go:145)、[游标推进](../internal/board/events.go:104)。

这不会自动证明现有看板快照错误，但说明分析功能应以持久事件分页重放为依据。建议保留已消费游标、读尽分页，或明确让客户端从持久 feed 补拉；SSE 负责提醒有变化。

历史区间查询还需拿到窗口开始前的最后状态，才能处理跨小时／跨日的阶段；统一时区、使用半开区间 `[start, end)` 裁剪，避免边界重复计时。事件索引应随确定的查询模式补充，本机样本的 `events` 尚无显式二级索引；当前数据量本身不足以证明有性能瓶颈。

## 建议的推进顺序与验收

### 第一阶段：交付任务阶段时间轴

先补历史身份与分页重放，再给现有“看板／依赖拓扑”增加“时间轴”。按工程分组、按任务执行批次展开，展示任务阶段、阻塞原因、失败、提交与合入节点；支持今天／指定日期与小时窗口。点击仍打开现有任务详情。

工程摘要优先回答：当前执行与阻塞任务、当日已合入任务、长时间未更新任务、评审／合并阶段驻留、失败与回退事件。来源缺少执行边界时显示事件活跃度，不填 AI 工时。

验收：跨日区间裁剪正确；同一编号重建后不串历史；缺失边界可见；超过 200 条的任务能查到末尾；累计指标能追到对应原始事件。

### 第二阶段：接入一个来源的真实执行记录

选择一个实际可验证、能提供稳定会话／轮次边界的数据来源，增加适配器与版本化事件契约。优先用工具明确提供的接口、hooks 或用户授权的本地记录；某个来源是否能提供这些字段，需要另行核实，截图没有给出证明。

复用现有中枢接收与 SQLite 持久化能力。通用状态上报继续服务进度汇聚，新遥测契约承载执行边界；按来源能力声明哪些信息可用。默认不需要采集完整提示词和输出正文。

验收：相同来源事件重放不重复；迟到和乱序可处理；崩溃无结束事件时显示未知；执行身份可关联到正确任务；usage 累计与增量不重复计数；明确展示接入覆盖范围。

### 第三阶段：做交付复盘与异常提示

执行数据稳定后再加入执行覆盖热图、活跃期间平均并发、已知 Token，以及工程／日期对比。结合任务依赖与交付证据解释异常，例如：执行批次反复失败、某前置任务长期阻塞后继、合并阶段积压。

与现有桌面路线图衔接，优先通知需要介入的阻塞、失败和关键交付变化。任何“长时间”阈值均应可配置并说明依据，先积累样本再调优。

验收：每个聚合值可下钻；缺数时仍可使用；高消耗不会自动等同高产出；通知能定位工程、任务、原因和下一步。

## 不建议照搬的部分

- 不把会话数、轮次数或 AI 累计时长作为首页首要成果指标，它们不能解释任务是否完成验收与合入。
- 不按更长工时、更多 Token 给工程或 Agent 排生产力名次。
- 不由持续的 `working` 状态补满整段 AI 执行时间，也不把离线与未知片段归为人的等待。
- 不先铺满多个 IDE 适配器，再解决事件身份、去重和口径；先完成一个来源的闭环。
- 不直接重用“取消／已完成”的轮次状态来改写 maw 任务终态，两者生命周期不同。
- 不重做整套视觉风格。现有中英双语、主题、工程导航、详情抽屉和桌面复用方式均可延续。

## 补充：统一管理多款客户端与自动派发

### 综合判断

“一个中枢＋工具接入器”符合 maw 的本机任务中枢定位。截图补的是过程观测，新增方案补的是任务执行控制；两者合起来形成“任务进入 → 领取／派发 → 执行 → 验收 → 回顾”的闭环。

但自动派发的缺口不只在每款工具的启动命令，还包括节点容量、执行身份、取消与恢复、明确的结果契约。建议保留原有客户端主动领取方式，在同一任务流上增加受控执行能力。

| 层次 | 现有基础 | 新增内容 |
| --- | --- | --- |
| 任务编排 | 蓝图、依赖、写盘冲突检查、领取与提交合入 | 指定任务／节点的绑定与能力匹配 |
| 节点管理 | 工程内 Agent 注册与状态 | 本机全局执行节点、入口探测、能力、容量与可用性 |
| 执行控制 | 当前由客户端主动执行与上报 | 接入器、运行批次、进程监督、取消、恢复与重试决策 |
| 结果与观测 | 代码验收路径、事件库、看板与详情 | 统一交付清单、执行事件、时间轴与用量覆盖 |

### 需要调整原方案的六个地方

**1. 接入器按协议／工具系列复用，节点按实例登记。**

同一接入器可以管理多个节点；同一品牌的桌面入口与 CLI 入口也可能需要不同实现。WorkBuddy 与 WorkBuddy AI 可先分别登记，核实真实协议后再决定是否共用接入器。无需先假设恰好五套实现。

现有 `agents` 主键是 `(project_id, id)`，表示工程内工作者，不能直接当作全机节点资源表。建议新增全局 `node_id`，关联现有工程内 Agent；保留 `{应用}-{工程}-{序号}` 的工作者命名。固定节点名可以是 `workbuddy-01`，但不能直接取代现有身份协议。

证据：[Agent 表](../internal/db/db.go:89)、[身份生成](../internal/identity/name.go:10)。现有自动识别还将部分 WorkBuddy 环境归为 `codebuddy`，进一步说明应用展示名与执行身份应分开。

**2. “可用”至少包含入口、鉴权与容量三件事。**

建议节点记录入口路径／版本、接入模式、能力集、探测时间、鉴权状态与执行槽。能力按实际验证声明，如自动启动、结构化事件、取消、恢复、usage；未知不填成支持。

“在线”“有空闲槽”“已登录”分开显示；人工接入节点可以在线但不支持自动派发。多个入口是否共享账户配额也应保持未知，未确认前不要把每个 App 都计作独立容量。

**3. 在原领取机制上扩展，不建立第二套独立队列。**

当前 `Next` 依据依赖、写盘冲突和亲和性选择任务，并在事务中记录归属；它没有指定任务 ID 的入参。未来从界面点选某题派给某节点时，不能先选 A，再无条件调用可能领取 B 的 `next`。

建议把“选择可执行任务”与“原子绑定任务实例、节点槽和 run”抽成共同逻辑。人工客户端继续拉取；自动执行器消费同一套已绑定任务。指定任务也必须通过原调度约束。

证据：[Next 入口](../internal/app/worker_cmd.go:18)、[选择与领取](../internal/app/worker_cmd.go:67)、[调度约束](../internal/schedule/schedule.go:55)。配置中已有 `[launcher] mode = "manual"`，当前代码未见消费它以启动这些客户端的业务路径，不能按该配置认定启动器已交付。

**4. 工作目录沿用现有复用策略，但并发容量必须有明确边界。**

maw 当前是每 Agent 一个持久 worktree，跨题复用；并非每题新建一个。保留此设计即可，但同一 Agent／目录不能同时运行两次写入任务。节点有多个执行槽时，各槽需要独立工作者身份与目录。

`max_parallel` 当前仅作看板参考，`Next` 明确不以它卡槽。后台自动领取不能直接假定已有容量限制，需补节点槽与全局资源限制。普通文档若属于 Git 工程仍可用 worktree；真正独立的非代码任务再使用专用任务目录，不能只因产物是 Markdown 就另走存储路径。

证据：[容量说明与 worktree 路径](../internal/app/worker_cmd.go:53)。现有 `write_scope` 在提交时校验改动范围，属于交付约束，不能当作进程运行期间的文件系统沙箱，见 [范围检查](../internal/app/worker_cmd.go:354)。

**5. 执行结束、交付通过和任务完成分别判定。**

接入器报告进程退出与输出；验收器检查产物和验证证据；任务仍走现有提交、评审与合入流程。退出码 0 或模型自称完成，不足以直接写成 `done`。

建议统一交付清单至少包含任务实例／run、执行节点、摘要、产物路径、基线与提交标识（代码任务）、验证命令和结果、退出状态与失败原因。非代码任务需要定义适用的验收完成机制，现有 Git 提交合入路径不能直接覆盖所有调研或文档交付。

证据：[Submit 与 gates](../internal/app/worker_cmd.go:329)、[合入完成路径](../internal/app/merge_cmd.go:180)。

**6. 心跳超时先查执行是否仍在运行，再决定重派。**

当前 stale-agent 处理可能释放任务，但自动执行器断联不等于其进程停止。若直接在同一目录重派，旧进程仍可能继续写入。未来需为每次 run 建立租约与代际标识，限制旧 run 的状态提交，并由执行监督器核实进程树停止后才复用目录／释放资源；代际标识本身阻止不了旧进程直接写文件。

派发后“是否启动成功”不确定时先对账，不自动重复启动；取消也须等待确认并保留部分结果。鉴权失败、等待用户、限流、模型失败与验收失败应分别处理。现有 `attempts` 同时受领取与部分失败路径影响，新增重试策略应使用独立 run 记录。

证据：[过期恢复](../internal/app/heartbeat.go:11)、[领取增长 attempts](../internal/app/worker_cmd.go:89)。ZCode 官方批任务文档也明确提醒外部启动器管理超时、进程树清理与独立评分；这部分成本不能全交给 CLI。

### 合并后的推进路线

| 阶段 | 可交付结果 | 核心验收 |
| --- | --- | --- |
| A：节点与执行契约 | 节点列表、能力探测结果、任务实例／run、统一交付格式；人工接入继续可用 | 同一节点跨工程不重复计容量；指定题绑定正确；未知能力可见 |
| B：一个 CLI 的完整闭环 | 共用调度约束，启动、事件采集、结果回收、验证、取消与恢复对账 | 不重复启动；容量受控；取消后旧进程不能继续占用复用目录；退出成功不绕过验收 |
| C：运行观测与时间轴 | 将 B 的真实执行事件与既有任务阶段事件展示在同一时间轴，区分来源与完整性 | 可追到 run 与产物；断线不伪造等待；历史分页与跨日边界正确 |
| D：扩展工具与自动选节点 | 复用已稳定契约扩展其他来源，按能力、容量和用户偏好选择 | 每个接入器分别通过同一组契约验收；不支持的能力可降级 |

阶段 A 同步处理前文的历史身份与事件分页问题；已有事件的任务阶段视图可在 A／B 期间逐步交付，无需等所有工具接完才可用。阶段 B 选哪个 CLI，由本机探测和最小任务验证决定，暂不因官方文档看起来丰富就锁定供应商。

自动派发应是用户可选择的接入模式，保留现有主动领取与人工验收方式。首轮不扩展云端账号体系、不接管现有桌面聊天、不用界面自动化承担核心调度可靠性。

本补充仅更新设计分析和官方来源核实，没有安装 CLI、改变登录状态、启动后台执行器或派发任务。未新增运行代码，因此未重复运行上一轮已通过的代码测试；已检查文档引用目标存在。
