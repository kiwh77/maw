# 标准任务卡规范（TASK-SPEC v1）

**适用**：所有进 maw 蓝图的 `[[task]]`，以及 `maw next` 生成到 worktree 的 `.maw/TASK.md`。
**依据**：2026-10-21 实测 106 题（`docs/DIAGNOSIS-20261022.md`、`docs/TASK-DESIGN-20261022.md`）。
**一句话原则**：**卡片是索引，不是文档。** 它负责让 agent 在 5 分钟内知道「做什么、从哪读、怎么算完、不许碰什么」，
细节一律放在 `read_scope` 指向的文件里，不塞进卡片。

---

## 1. 字段清单（三级）

| 级别 | 字段 | 一句话定义 | 现状 |
| --- | --- | --- | --- |
| **L1 必需** | `id` | 稳定唯一标识，一经合入不得复用 | ✅ 已支持 |
| **L1** | `title` | 动词开头的**可交付结果**，≤30 字，不含无终点词 | ✅ 已支持 |
| **L1** | `goal` | 为什么做这题 + 做完世界有什么不同（≤2 句） | ⚠️ 需扩展 |
| **L1** | `write_scope` | 允许改动的路径，≥1 条 | ✅ 已支持 |
| **L1** | `acceptance` | ≥1 条**可判定**断言（能回答是/否） | ✅ 已支持 |
| **L1** | `verify` | ≥1 条可执行命令，或 `manual: <人怎么验>` | ⚠️ 需扩展 |
| L2 推荐 | `deps` | 依赖题；**决定并行度，是拓扑的关键** | ✅ 已支持 |
| L2 | `read_scope` | 开工前必读的文件，≥1 条 | ✅ 已支持（**但卡片不展示**） |
| L2 | `priority` / `merge_order` | 序位键，决定同盘串行顺序 | ✅ 已支持 |
| L2 | `not_doing` | 明确不做的事（负面约束，防过度实现） | ⚠️ 需扩展 |
| L3 可选 | `artifact` | 非代码产物（样本/文档/数据），走产物入库通道 | ⚠️ 需扩展 |
| L3 | `size_hint` | 预估文件数/行数，用于拆题告警 | ⚠️ 需扩展 |
| L3 | `lane` | 模块簇名，显式化上下文亲和 | ⚠️ 需扩展 |

> 「需扩展」的字段：解析层（`blueprint.TaskSpec`）尚无对应字段，但 `db.Task.Extra` 是 `map[string]any`，
> **可以零 schema 迁移先落 Extra**。落地时按第 7 节的兼容写法过渡。

## 2. L1 字段的判定标准（这是规范的核心）

### 2.1 `title` —— 必须是可交付结果，不是动作方向

- ✅ `实现质量领域类型与端口` / `修复候选产物与控制对象的存储布局冲突`
- ❌ `优化质量流程`（无终点）/ `完善文档`（无验收）/ `支持新格式`（范围不明）
- **模糊词黑名单**：优化、完善、改进、支持、处理、调整、初步、相关、以及、等、后续
  —— `plan check` 命中即告警，因为这类词让 agent 无法判断「做到哪算完」。

### 2.2 `goal` —— 当前最大的信息缺口

实测：卡片里完全没有「为什么做这题」，agent 只能从 title 猜意图，容易过度实现或跑偏。

格式（两句话，各一行）：

```
goal = "现状：<哪里有问题，可引文档/issue>。目标：<做完之后什么变了，可用什么观察>。"
```

- ✅ `现状：旧格式规划被误判为空导致全书范围被截断。目标：读取旧格式不再写副作用，且全书范围不变。`
- ❌ `提升质量`（没有现状，也没有可观察的变化）

### 2.3 `acceptance` —— 必须可判定

判据：**不看代码、不问你，只读这一条就能回答「过了没有」**。

- ✅ `旧格式不再被误判为空且全部读取均无写副作用`
- ✅ `缺块时覆盖率不得显示为 100%`
- ❌ `体验更流畅` / `代码结构更清晰` / `feature A works`

每条断言应尽量包含**判定的观察点**（哪个接口、哪个页面、哪个数字）。

### 2.4 `verify` —— 把「怎么证明」与「断言本身」分开

现状问题：某工程把 `Verify: uv run --locked pytest ...` **混在 acceptance 字符串里**，
机器无法提取、无法自动执行，只能人读；实测工程里曾出现大量缺验收的情况。

规范形态：

```toml
verify = [
  "uv run --locked pytest tests/test_quality_storage.py -q",
  "cd web && npx --no-install tsc --noEmit",
]
```

- 允许 `manual: <步骤>` 表示只能人验（例如 UI 交互），但**必须有**，不允许空。
- **不允许** `verify = []` 或 `verify = ["none"]`——那等于没有验收。

### 2.5 `not_doing` —— 一条负面约束抵三条正面说明

实测中的过度实现多发生在「顺手重构相邻代码」。写清楚边界比写清楚目标更省事。

```toml
not_doing = ["不改现有 HTTP 路由签名", "不新增依赖", "不动 data/ 下的既有产物"]
```

## 3. 卡片渲染规则（`TASK.md`）

**正文 ≤ 40 行**，超了说明把文档塞进了卡片。结构固定为 8 段：

```markdown
# NW-030: 实现不可变质量产物与操作日志存储

## Goal
现状：…… 目标：……

## 完成判据
- [ ] 重建 cache 索引后报告/决策可查且 ID 不变
- [ ] 不可覆盖既有产物，损坏或逃逸路径明确失败

## 验证命令
- `uv run --locked pytest tests/test_quality_storage.py -q`

## 先读这些（read_scope）
- `docs/architecture/quality-first-v2.md`
- `docs/contracts/quality-first-v2.md`

## 上游已交付（deps）
- NW-020 实现质量领域类型与端口 —— 验收：所有核心对象可往返序列化

## 可写范围（write_scope）
- `backend/novel_writer/quality/storage/**`
- `tests/test_quality_storage.py`

## 不要做（not_doing）
- 不新增依赖；不改已有存储格式

## 协议
里程碑 `maw progress -m "..."`；完成 `maw submit`；随后可 `maw merge --yes`。
```

**与现状的三处差别**（全部是「数据已有但没送到」）：
1. 增加 `## Goal`、`## 先读这些`、`## 上游已交付`、`## 不要做`；
2. `read_scope` **必须渲染**（现在只落在 `task.json`，卡片看不见）；
3. deps 段落自动从库里取「依赖题标题 + 验收」，不需要人手写。

## 4. `plan check` 校验规则（机器可判）

| # | 规则 | 级别 | 依据 |
| --- | --- | --- | --- |
| 1 | `title` 命中模糊词黑名单 | ⚠️ 告警 | 无法判断完成 |
| 2 | `acceptance` 缺失，或全部条目不含观察点 | ❌ 错误 | 某工程 0/65 可判定 |
| 3 | `verify` 缺失 | ❌ 错误 | 同上 |
| 4 | `write_scope` 为空 | ❌ 错误 | 已有 |
| 5 | `write_scope` 顶层跨 ≥3 个模块目录 | ⚠️ 告警（拆题信号） | 单题应聚焦 |
| 6 | 单题 `write_scope` 含共享文件（lockfile/路由表）却未在 `[shared_files]` 声明 | ⚠️ 告警 | 冲突高发 |
| 7 | **波次无 deps 的题 = 0**（单入口） | ⚠️ 告警 | 某工程只有 1 个入口 |
| 8 | **依赖链深度 > 8** | ⚠️ 告警 | 实测深度 15、53% 空转 |
| 9 | 两题写同一文件但相互无 `deps` | ⚠️ 告警 | 靠 priority 串行易漏 |
| 10 | 单题预估文件数 > 20 | ⚠️ 告警（拆题信号） | NW-010 提交 6735 文件 |

规则 7、8 的输出应写成**并行宽度报告**：`deps 深度 N / 入口 M / 各层宽度 [..] / 理论最大并行 K`。
压蓝图时就能看见「这波最多几个能同时干」。

## 5. 反模式（全部来自实测）

| 反模式 | 实测证据 | 改成 |
| --- | --- | --- |
| **一题多交付物** | NW-010 一次合并 129,167 行 / 6,735 文件（脚本+样本+文档混在一起） | 拆成「脚本与清单」+「样本产物入库」 |
| **验收不可判定** | 实测工程几乎无题含可执行验收 | 每条断言带观察点，另设 `verify` |
| **写盘范围跨度过大** | 单题 write_scope 覆盖多模块 | 拆题或声明 `not_doing` |
| **依赖串成一条长链** | 某工程曾出现深度 15 的长链、单入口 | 每波保留 ≥2 个无 deps 入口；尾部避免 1 宽 |
| **卡片当文档用** | 现状卡片无 read_scope，正文靠人补 | 卡片只放导航，细节进 read_scope 文件 |
| **`Verify:` 混在验收文本里** | 某工程大量题混写 | 独立 `verify` 字段，机器可执行 |

## 6. 粒度基线（用于判断「要不要拆」）

实测参考值（约 40 次合并）：

- 单题改动：**中位 993 行 / 3 个文件 / 5.3 分钟**
- 合理区间：**200–1,500 行、1–6 个文件、单模块内**
- 拆题信号：>20 文件、>2,000 行、跨 ≥3 个模块、或需要两种以上验证手段

**注意**：粒度不是越小越好。实测单题中位 5.3 分钟、41 题串成 15 层深链，
**细粒度会放大交接成本**（每次交接平均等 6.1 分钟）。宁可略粗、少交接。

---

## 7. 与现状的兼容写法（立即可用，不改代码）

在解析层支持新字段之前，用以下写法**等价表达**，保证信息不丢：

| 目标字段 | 当下写法 | 机器提取 |
| --- | --- | --- |
| `goal` | 放在 `acceptance` 第 1 条，前缀 `现状：…目标：…` | 人读；暂不参与校验 |
| `verify` | 保留 `Verify: <命令>` 前缀（已有工程在用） | 可按前缀提取，后续升为独立字段 |
| `not_doing` | 追加到 `acceptance` 末尾，前缀 `不要：` | 人读 |
| `size_hint` | 暂时不写，由事后统计反推 | — |

升级路径：解析层加字段 → `plan check` 启用第 4 节规则 → 卡片渲染加 4 段 → 老的兼容写法保留为 fallback。

---

## 8. 落地顺序

1. **卡片渲染补 4 段**（read_scope / deps 摘要 / goal / not_doing）——数据已在库，成本最低，收益最直接。
2. **`plan check` 加规则 2、3**（验收可判定 + verify 存在）——立刻让缺验收的蓝图暴露。
3. **`plan check` 加并行宽度报告（规则 7、8）**——排布问题在压入前可见。
4. **解析层加 `goal`/`verify`/`not_doing`**，兼容写法保留。
5. 规则 5、6、9、10 视噪声再启用，避免一开始告警过多被忽略。
