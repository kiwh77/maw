# maw vNext 升级与迁移说明

> 语言：简体中文（本目录暂无英文版）｜适用版本：从 0.4.0 及更早版本升级到 vNext

**结论：升级不是「换个二进制」——它是「停掉所有旧写端 → 做一次 WAL 一致的备份 → 让新写端迁移 → 校验」。
四步里任何一步被跳过，都可能得到一个「看起来能跑、其实数据已经被旧写者覆盖」的库。**

本文只讲操作与判据，不重复架构推理（见 [架构规划](../../ARCHITECTURE_VNEXT.zh-CN.md) §14）。

## 版本兼容

库的写入资格由两个字段决定，二进制每次写库前都会读一遍：

| 字段 | 位置 | 含义 |
| --- | --- | --- |
| `schema_version` | `meta` 表 | 库的数据结构版本；高于当前二进制能推进到的版本时**禁止写入** |
| `min_writer_version` | `meta` 表 | 库要求的最低写者版本；二进制低于它时**禁止写入** |

三种组合的处理：

| 情况 | 现象 | 处理 |
| --- | --- | --- |
| 库版本 = 二进制版本 | 正常读写 | 无需操作 |
| 库版本 < 二进制版本 | 需要推进迁移 | 走本文「升级步骤」 |
| 库版本 > 二进制版本 | 报 `schema 版本高于当前二进制` | **不要写它**；换回新二进制，或用备份回退 |
| 二进制 < `min_writer_version` | 报 `库要求更高的写者版本` | 升级二进制，不要试图绕过 |

`min_writer_version` 为空表示这个库由**不写该字段的旧二进制**创建或打开过。这类库里两个保护字段都不可信，
所以下面的「停旧写端」不是建议而是前提。

## 停旧写端

0.4.0 及更早的写者**不读** `min_writer_version`，也不检查 `sqlite_master`：它会无条件
`CREATE TABLE IF NOT EXISTS` 并 `INSERT OR REPLACE` 写回 `meta.schema_version`。
也就是说，新字段保护不了新库——一个还在跑的旧 `maw` 进程足以把刚迁移好的库改回旧样子。

因此破坏性升级的窗口里必须满足：

1. 所有旧 `maw` 进程已退出（含 `maw board --serve`／`maw serve` 中枢、桌面端拉起的那个中枢、以及各个 Agent 会话里的 `maw` 命令行）。
2. 没有仍在占用的受管 Run、未释放的资源占用、未过期的锁。
3. 新写端在迁移前自己再断言一次「运行已排空」；断言不通过就**拒绝隐式迁移**，不会「先迁了再说」。

排空检查认这些占用者（宁可误报也不放过）：计入占用的 Run（含 `unknown` 阶段、以及**失败但进程停止未确认**的 Run）、
未释放的资源占用（节点槽／工作目录／合并锁）、在飞任务（`in_progress` / `self_check` / `conflict`）、
非 idle 或仍绑着任务的 Agent、未过期的路径锁。

被拦住时的正确做法是**去把这些占用收尾**，而不是找开关跳过。真的收不了（例如进程已失联）时，
按「unknown 处置」留下证据再处理。

## 一致备份

**不要用 `cp ~/.maw/maw.db` 备份。** 库跑在 WAL 模式下，直接拷主库文件会丢掉尚未 checkpoint 的帧，
拷出来的可能是一个「少最后几笔事务」的库，而它看起来完全正常。

maw 统一走 `VACUUM INTO`：它在读事务里生成一个一致快照，把 WAL 里未合并的帧一起落进目标文件。
**当库需要推进迁移时**（`schema_version` 落后于当前二进制），升级入口 `maw init --upgrade`
以及任何会隐式推进迁移的写入口都会按这个方式先备份到 `<库路径>.pre-migrate-<UTC 时间戳>.db`，
备份完还会校验一遍：

- `PRAGMA integrity_check` 必须是 `ok`；
- 备份能被当前二进制恢复（写者闸门通过）；
- 与源库逐表比对：schema 版本一致、表清单一致、每张表行数一致；
- 引用一致性检查的问题清单与源库一致（跨表指针断了但行数对得上，靠这一步才能发现）。

库已经是最新 schema 时不会产生备份——这类升级没有数据变更，也就不需要备份。
备份校验失败会直接中止迁移并报错——这时候库还是原样，改完问题重试即可。

手工备份也用同一个方式：

```bash
sqlite3 ~/.maw/maw.db "VACUUM INTO '/tmp/maw-backup-$(date -u +%Y%m%dT%H%M%SZ).db'"
```

## 升级步骤

```bash
# 0. 确认版本与库状态
maw --version
maw doctor --json

# 1. 停掉所有旧进程（中枢、桌面端、各 Agent 会话里的 maw）
#    确认没有残留：ps 里看不到 maw；看板不可访问

# 2. 升级
maw init --upgrade

# 3. 校验
maw doctor --json     # issues 为空
maw board --serve     # 页面能打开，任务数与升级前一致
```

`maw init --upgrade` 的三种结局都要认清：

| 结局 | 含义 | 下一步 |
| --- | --- | --- |
| 成功 | 已备份、已校验、已迁移 | 正常使用；备份文件留着，别急着删 |
| 拒绝迁移（运行未排空） | 断言没过，库未被改动 | 回去收尾占用者，然后重跑 |
| 迁移失败但已回滚 | 迁移中途出错，已用备份原子恢复 | 看错误原文定位；库是迁移前状态 |

## 故障恢复

恢复的语义是**整库原子替换**，不是「把表补回去」：

1. 先校验备份可用（完整性、写者闸门、引用一致性）。
2. 把备份复制成目标同目录的 `.restore-tmp`。
3. **删掉目标库的 `-wal` 与 `-shm`**。这一步不能省：旧日志属于被替换的库，留着它会在下次打开时被回放，
   把刚恢复的内容又盖掉。
4. `rename` 上位。rename 是原子的，所以要么看到旧库，要么看到恢复后的库，不会看到半个。

执行前提只有一个，但必须满足：**此刻没有写者**。恢复不做并发保护——它是「已经出事之后」的动作。

恢复之后仍要跑一次 `maw doctor --json`；`issues` 不为空说明备份本身也有问题，需要换更早的备份。

## unknown 处置

`unknown` 是「不知道」，不是「失败了」，更不是「结束了」。规则只有一条：

> **`unknown` 不得直接落终态（`E232`）。观测缺失不是停止证据。**

由此推出三条必然后果：

- `unknown` 期间占用继续保留：节点槽不释放、工作目录不重新分配。否则同一个目录上可能同时跑两个进程。
- 心跳丢失本身只让人进 `unknown`，不能据此判定进程已停、更不能补造结果。
- 心跳恢复也不能「自动当作没事」：必须有一条能回到原始事实的证据，才允许解除。

解除 `unknown` 的判据是**证据**，证据有三种来源，且人工来源必须留痕：

| 来源 | 形式 | 要求 |
| --- | --- | --- |
| `process` | 按 PID + 启动时间确认原进程仍在／已不在；进程组是否清空 | 必须给出稳定引用（日志位置、探针输出） |
| `runtime` | 中枢自己的运行时事实（journal 记录、退出记录） | 同上 |
| `manual` | 人工核对结论（处置单号、现场记录） | **必须记录处理人和时间**，只写结论不算证据 |

三种结局，按证据强弱区分：

1. 确认后代进程已停止 **且** 结果已判定 → 补录终态（记录证据引用）。
2. 确认后代进程已停止但结果无法判定 → 保持 `unknown`，等人处置；不要猜一个结果写进去。
3. 进程仍在运行，或 PID 已被复用且后代未确认 → 继续保留占用，转人工停止流程。

「PID 复用」是最容易看错的一种：按 PID 找得到进程不代表那是原来那个进程，
只有启动时间也一致才算「还在跑」。

## 回退与降级

**新库不能拿旧二进制去写。** 库版本高于二进制时会报 `ErrSchemaAhead`（`schema 版本高于当前二进制`），
`min_writer_version` 更高时会报 `ErrWriterTooOld`。这两个错误是保护，不是 bug：

- 旧二进制不认识新表/新列，它的 `CREATE TABLE IF NOT EXISTS` 会「成功」，然后写进一份结构不完整的记录；
- 它还会把 `meta.schema_version` 覆盖成自己认识的值，于是库看起来「降级成功」，实际数据已经不一致。

所以正确的回退只有一条路：**用升级前的备份整库恢复，再用旧二进制打开。**

maw 目前**没有** `maw db restore` 这类子命令（备份由升级入口自动做，恢复是需要停写的文件级操作）。
回退就是在确认没有写者之后，按 Restore 的四步手工执行：

```bash
# 1) 确认没有 maw 进程在跑（中枢、桌面端、各会话里的 maw 都算）
# 2) 校验备份本身可用
sqlite3 /path/to/maw.db.pre-migrate-<ts>.db "PRAGMA integrity_check;"   # 期望 ok
# 3) 原子替换：先落到同目录临时文件，再 rename 上位
cp /path/to/maw.db.pre-migrate-<ts>.db ~/.maw/maw.db.restore-tmp
# 4) 旧日志必须失效，否则会被回放到恢复结果上
rm -f ~/.maw/maw.db-wal ~/.maw/maw.db-shm
mv ~/.maw/maw.db.restore-tmp ~/.maw/maw.db

maw --version        # 确认是旧版本
maw doctor --json    # issues 为空
```

第 3 步用 `cp` 而不是 `mv` 是为了保留备份原件：恢复失败时你还需要它。第 4 步的 `rm` 只删 `-wal` / `-shm`，
不要顺手删主库文件。

回退之前先问一句：**升级后有没有新写入？** 如果有，那些写入只存在于新库里，回退等于丢掉它们。
这种情况下更好的做法是升级二进制继续往前，而不是回退。

## 发布说明要点

本版本对外承诺的范围：

- **支持**：人工领取闭环（`next` / `progress` / `submit` / `merge`）、跨工程看板与观测 API、静态导出只读页面。
- **有条件支持**：受管单次执行——仅 macOS，且需显式指定任务与节点；自动派发默认关闭。
- **不支持**：受管模型调用（无实测证据）、非 macOS 平台的受管执行、多机共享库。
- **已知问题**：浏览器验收里 `vn-981` 的键盘导航用例在未选工程时失败（用例期望与既有行为不一致），
  已登记在 [平台支持矩阵](../verification/vnext/release/platform-matrix.zh-CN.md) §4，CI 不会绕过它。

升级到本版本前请按本文顺序执行：停旧写端 → 一致备份 → 迁移 → 校验。跳过备份的升级没有回退路径。
